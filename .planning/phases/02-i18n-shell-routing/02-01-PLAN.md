<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → proxy.ts | Untrusted request URL (including arbitrary/locale-shaped path segments) crosses into locale detection + redirect construction |
| URL segment → i18n/request.ts | The `[locale]` path segment becomes the key for message-file dynamic import and `<html lang>` |

## STRIDE Threat Register

ASVS Level 1 · block on: high

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2-01 | Spoofing/Tampering | proxy.ts + i18n/request.ts locale param | high | mitigate | `hasLocale(routing.locales, param)` validates the locale against the `['de','en']` allowlist before use; `notFound()` on invalid — no attacker-controlled value reaches the redirect target or the dynamic `messages/${locale}.json` import (prevents open redirect + path traversal) |
| T-2-02 | Tampering | Accept-Language header | low | accept | D-05 rejects Accept-Language entirely — the root redirect is always `/de` regardless of the header, so header injection has no locale-selection surface. Accepted: no code path consumes the header. |
| T-2-03 | Information Disclosure | rendered `<html lang>` | low | accept | Locale is derived from the URL segment only; `<html lang>` reflects the URL. There is no hidden locale state (no cookie/localStorage) that could leak — the static guard (tests/invariants/no-locale-from-state.sh) structurally enforces this. |
| T-2-SC | Tampering | npm install next-intl | high | mitigate | package-legitimacy gate: next-intl is [SUS] (too-new false positive on a 5-yr / 5M-weekly-download library). Blocking human-verify checkpoint (Task 0) precedes install; verify at npmjs.com/package/next-intl. |
</threat_model>
