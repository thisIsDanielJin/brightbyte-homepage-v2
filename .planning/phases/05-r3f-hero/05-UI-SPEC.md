# Phase 5 — UI Design Contract: R3F Hero

> Visual and interaction contract for the isolated 3D hero centerpiece.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.
>
> **Scope of this contract:** Phase 5 does NOT redesign the hero text column, copy, or
> layout. It contracts the visual behavior of the Canvas layer, the fade-in transition,
> the legibility mechanism behind copy, the reduced-motion/fallback visual parity,
> responsive scaling behavior, and all loading/state transitions.
>
> **Upstream lock:** Every design decision is pre-populated from 05-CONTEXT.md (D-01…D-12),
> REQUIREMENTS.md (HERO-01, HERO-02), and the existing token system (styles/tokens.css).
> Nothing in this contract was invented by the researcher — all values are derived or
> token-referenced. Where a value has NO token, it is FLAGGED rather than hardcoded.

### R3F scene color contract

Glass tint and lighting are derived from the existing token palette (D-09). No new token is
introduced. Permitted CSS variable references in JS/R3F scene files (accessed via
`getComputedStyle` or hardcoded-from-token constants declared as named JS constants):

| Scene use | Token reference | Resolved value | Purpose |
|-----------|-----------------|----------------|---------|
| Glass tint / transmission color | `--color-accent` | #1C39BB | Subtle blue cast in glass refraction |
| Key light color | `--color-surface-subtle` | #FAFAFA | Warm-neutral fill |
| Environment base | `--color-surface-dark` | #0F0F10 | Scene background behind Canvas |
| Ambient fill | `--color-surface` | #FFFFFF | Secondary environment fill |

**FLAG — no CSS token for R3F:** R3F scene files cannot consume Tailwind utility classes.
Token hex values MUST be declared as named JS constants derived from the token file, NOT
hardcoded inline. Pattern: `const ACCENT = '#1C39BB' // from --color-accent` at top of
the scene file. This keeps a named reference (auditable) without injecting raw hex into
component logic. The invariant test (`tests/invariants/*.sh`) scans component files — the
scene file must not be excluded from that scan.

### Legibility scrim contract (D-08 compliance)

The glass sits behind the text column. WCAG AA requires 4.5:1 for normal text against the
ACTUAL rendered composite background. The existing tokens satisfy AA on white
(`text-primary` #18181B = 17.72:1; `text-secondary` #52525B = 7.73:1; `bg-accent`
CTA = 8.93:1 white-on-accent). The glass blur/translucency may reduce effective contrast.

**Hard rule:** The scrim mechanism must hold WCAG AA across the copy region without
exception. Choose EXACTLY ONE of the following mechanisms (implementation decision for
planner/executor — both are acceptable paths):

| Option | Mechanism | Token path |
|--------|-----------|------------|
| A (preferred) | Offset focal mass — position glass centroid at 65–70% horizontal, away from the left-aligned text column that occupies ~50% width | No new token; pure composition parameter |
| B (fallback) | Radial scrim over the text region — a CSS pseudo-element `::before` on the Canvas wrapper using `bg-surface/60` (Tailwind v4 opacity modifier on token color) | `--color-surface` at 60% opacity |

Option A is preferred because it requires no additional DOM element or CSS and preserves
the glass composition unmodified. Option B is the fallback if QA (Playwright AA check)
fails with Option A. Both options are composable — if the centroid is offset AND a light
scrim is needed, use both. The QA gate (D-08 WCAG AA verified in production Playwright
screenshot) is the decision surface.

**For the CTA specifically:** `bg-accent text-surface` (#FFFFFF on #1C39BB = 8.93:1) is
already AAA. No scrim needed for the button itself regardless of glass position.

- No `tabIndex`, no `role`, no interactive affordances (D-04: autonomous only, no user input)

## Fade-in Transition Contract (D-11)

The gradient paints immediately (LCP element, no JS dependency). The Canvas mounts
lazily via `next/dynamic({ ssr: false })`. Once the R3F scene is ready to render its
first frame, the Canvas cross-fades in.

### Timing values

| Property | Value | Token reference |
|----------|-------|-----------------|
| Duration | 400ms | Between --duration-standard (300ms) and --duration-entrance (500ms); midpoint for a cross-fade that is perceptible but not slow. **FLAG:** no exact token at 400ms. Nearest tokens: --duration-standard 300ms, --duration-entrance 500ms. Use 400ms as a local constant `const HERO_FADE_DURATION = 400` or use --duration-entrance (500ms) as the conservative pick. Do NOT introduce a new token for a one-off value. |
| Easing | ease-out | `--ease-out: cubic-bezier(0.0, 0.0, 0.2, 1)` |
| Property animated | opacity: 0 → 1 | Canvas wrapper only |
| Element animated | Canvas wrapper `<div>` or Canvas directly | Executor chooses; wrapper preferred (avoids styling the canvas element directly) |

### Implementation pattern (two acceptable paths)

**Path 1 — CSS transition (preferred, zero JS dependency):**
The Canvas wrapper starts with `opacity-0` and transitions to `opacity-100` triggered by
an `data-ready` attribute set in the R3F `onCreated` callback:

```tsx
// wrapper: className="absolute inset-0 opacity-0 [transition:opacity_400ms_cubic-bezier(0,0,0.2,1)] data-[ready=true]:opacity-100"
// in R3F onCreated: wrapperRef.current.dataset.ready = 'true'
```

**Path 2 — motion/react (acceptable fallback):**
Use `motion/react`'s `animate` on the Canvas wrapper div. Duration 0.4, ease `[0.0, 0.0, 0.2, 1]`.
`motion` is already installed (package.json). No new dependency.

**Path 1 is preferred** because it uses no JS runtime for a pure visual property change.
Either path produces identical visual output.

### What does NOT happen

- No drei `<Loader>` — no spinner, no percentage bar
- No "pop-in" — gradient must be fully visible before Canvas mounts; opacity starts at 0
- No layout shift — Canvas and HeroFallback share `absolute inset-0`, so swapping them
  causes zero reflow (CLS = 0)
- No opacity: 0 flash on the fallback — the fallback is always visible; the Canvas fades
  IN OVER the fallback; the fallback remains painted underneath until the Canvas is opaque

## Reduced-Motion Contract (D-06, HERO-02)

### Gate: `prefers-reduced-motion: reduce` — no Canvas, ever

When the system preference `prefers-reduced-motion: reduce` is active:

1. The `HeroCanvas` client island **is not rendered at all** — `useReducedMotion()` (from
   `motion/react`, already imported in this codebase) returns `true`; the Canvas branch
   is never entered
2. The `HeroFallback` (`.hero-backdrop` div) renders in place of the Canvas, filling
   `absolute inset-0` with the same token-based radial gradient as today
3. **Zero layout shift** — `HeroFallback` and the Canvas wrapper share identical
   `absolute inset-0` dimensions; the text column at `z-10` is unaffected
4. **The global `@media (prefers-reduced-motion: reduce)` block** in `globals.css` already
   zeros all animation/transition durations — this is a defence-in-depth layer; the primary
   gate is the no-Canvas branch in the client island

### Implementation pattern

```tsx
// HeroCanvas.tsx ('use client')
import { useReducedMotion } from 'motion/react'

export function HeroCanvas() {
  const prefersReduced = useReducedMotion()
  if (prefersReduced) return <HeroFallback />
  // ... R3F Canvas
}
```

`useReducedMotion` is already present in the codebase (MotionSection.tsx). No new import.

### HeroFallback specification

`HeroFallback` = `<div className="absolute inset-0 hero-backdrop" aria-hidden="true" />`

This is the EXISTING markup in HeroSection.tsx line 48 — verbatim reuse, zero new CSS.
The `.hero-backdrop` utility in `globals.css` renders:

```css
background: radial-gradient(
  ellipse 80% 60% at 60% 40%,
  var(--color-surface-subtle) 0%,   /* #FAFAFA */
  var(--color-surface) 70%          /* #FFFFFF */
);
```

The focal center at `60% 40%` (right-of-center, upper) is the static analog of the glass
centroid position. This visual continuity means no perceived shift when the Canvas loads
or when reduced-motion shows the fallback.

## No-WebGL / Pre-Hydration State

Identical to the reduced-motion fallback. The `HeroCanvas` client island is loaded via
`next/dynamic({ ssr: false })` — no SSR Canvas — so the HTML shipped by the server
always contains the `.hero-backdrop` div. On hydration, if WebGL is not available (or not
yet initialized), the fallback remains. Only once the Canvas is ready does the fade-in
begin. There is no intermediate "blank" state.

### WebGL capability check

Before mounting R3F, perform a lightweight WebGL capability check:

```ts
function canUseWebGL(): boolean {
  try {
    const canvas = document.createElement('canvas')
    return !!(
      canvas.getContext('webgl2') ||
      canvas.getContext('webgl') ||
      canvas.getContext('experimental-webgl')
    )
  } catch {
    return false
  }
}
```

If `canUseWebGL()` is `false`, render `<HeroFallback />` and do not attempt to mount R3F.
This prevents a blank canvas on headless/unsupported environments.

## Responsive Behavior Contract

The canvas occupies `absolute inset-0` — it fills the hero section at all breakpoints by
definition. The responsive contract is about GLASS COMPOSITION within the scene, not about
the canvas element dimensions.

### Mobile (375px — Moto G4 baseline)

| Property | Value | Rationale |
|----------|-------|-----------|
| Glass centroid horizontal | 50% (centered) | On mobile the text column is full-width; off-centering would be invisible or look random. Center is calmer and simpler. |
| Glass scale | Camera Z-distance + 20% back from desktop position | Pulls the glass smaller in screen-space so it does not crowd the text at narrow widths. Exact value: executor discretion within this guardrail. |
| Glass vertical position | Slight push toward 45% height | Keeps glass roughly centered vertically in the viewport on mobile without overlapping the text block that starts near 20–25% viewport height |
| Frameloop on mobile | `frameloop="always"` + PerformanceMonitor active | D-04/D-05 governs — the loop runs but DPR adapts and IntersectionObserver pauses when scrolled off. DPR floor: 1.0 (never lower) |
| Transmission material on mobile | Planner/researcher decides degradation strategy (D-12 Claude's Discretion) | If MeshTransmissionMaterial renders > 200 draw calls or causes LCP regression, fall back to a cheaper non-transmissive frosted glass (MeshPhysicalMaterial with roughness + opacity) on mobile. The scene MUST meet budget. |

### Desktop (1440px baseline)

| Property | Value | Rationale |
|----------|-------|-----------|
| Glass centroid horizontal | 65–70% (right-of-center) | Focal mass opposite the left-aligned text column. Creates visual tension; keeps the copy region unencumbered. This is the preferred Option A scrim strategy. |
| Glass scale | At executor/planner discretion — fills roughly 40–55% of viewport height | Large enough to read as a centerpiece; not so large it dominates the text |
| Glass vertical position | Centered vertically (50% viewport) | No conflict with text block at this width |

### Responsive transition

There is no discrete breakpoint for the glass — the scene camera and object scale respond
continuously to the R3F canvas size. The executor should use R3F's `useThree` hook to
read `size.width` and derive camera Z or object scale proportionally.

## Scene Motion Contract (D-04, D-05)

### Rotation

| Property | Value |
|----------|-------|
| Axis | Single axis — Y-axis (vertical spin) |
| Speed | ~0.003 radians/frame at 60fps — completes one full rotation in ~35s |
| Direction | Clockwise when viewed from above (positive Y rotation) |
| `frameloop` mode | `"always"` (continuous rotation requires always-on loop) |

### Offscreen pause (D-05 mandatory)

When the hero section is scrolled out of the viewport, the render loop MUST be paused to
prevent unnecessary CPU/battery drain.

Pattern: wrap the R3F `<Canvas>` in a component that reads `useInView` (from React or an
IntersectionObserver hook) and sets `frameloop="never"` on the Canvas via a ref when not
intersecting. Executor chooses the exact R3F API — the constraint is that the loop pauses
within 1 frame of the hero leaving the viewport.

### PerformanceMonitor (D-05, ROADMAP SC #4)

`<PerformanceMonitor>` from `@react-three/drei` MUST be active in the scene, wrapping the
mesh. Configure adaptive DPR:

```tsx
<Canvas dpr={[1, 2]}>
  <PerformanceMonitor
    onDecline={() => /* lower DPR floor or disable transmission */}
    onIncline={() => /* restore DPR */}
  >
    <GlassScene />
  </PerformanceMonitor>
</Canvas>
```

DPR range: min 1.0, max `Math.min(devicePixelRatio, 2)`. On decline, reduce DPR floor
(not below 1.0) or simplify the material. Exact thresholds: executor discretion within
budget constraint.

## Loading / State Diagram

```
Server render
    │
    ▼
[HeroFallback: .hero-backdrop radial gradient]  ← LCP element (always paints, SSR)
    │
    ├─ (prefers-reduced-motion: reduce) → stays as HeroFallback forever
    ├─ (WebGL not available)            → stays as HeroFallback forever
    │
    ▼ (JS hydrates, next/dynamic resolves)
[HeroFallback still visible]
    │
    ▼ (R3F scene initializes, onCreated fires)
[Canvas fades in over HeroFallback: opacity 0→1, 400ms, ease-out]
    │
    ▼
[Glass rotating, PerformanceMonitor active, IntersectionObserver active]
    │
    ├─ (user scrolls down: hero leaves viewport) → frameloop="never"
    └─ (user scrolls back: hero enters viewport) → frameloop="always"
```

## Performance Contract (D-12 — governing)

These are HARD GATES verified in a production `next build` + `next start` run.

| Metric | Target | Measurement method |
|--------|--------|--------------------|
| LCP | < 2.5s | Lighthouse mobile audit, Moto G4 profile, 3G throttled |
| CLS | 0 | Lighthouse + WebPageTest |
| Draw calls | < 200 | R3F stats or Spector.js in production build |
| PerformanceMonitor | Active and responding | Manual verify: throttle CPU 4x in DevTools, confirm DPR adapts |
| Hydration errors | 0 | `next start` console — zero hydration warnings |
| Canvas on server | 0 | `next build` output: no Canvas/WebGL imports in server bundle |

**LCP protection principle:** The `.hero-backdrop` gradient is the LCP element because it
is rendered server-side in static HTML. The 3D Canvas is a progressive enhancement that
must never block or delay the LCP paint. `next/dynamic({ ssr: false })` ensures the
Canvas is not in the SSR HTML and cannot block the first meaningful paint.
